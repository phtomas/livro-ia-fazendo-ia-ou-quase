2. O que uma leitura rigorosa precisa distinguir

As frases abaixo são notas de precisão, não uma lista de erros atribuídos automaticamente ao documento de origem. Onde o guia simplifica, explicamos as condições em que a simplificação funciona.

TemaFormulação rigorosaFonte
Previsão de tokensÉ um objetivo importante em modelos autorregressivos; não caracteriza sozinho toda a família de modelos de linguagem.[F1], [F2]
TransformerO artigo de 2017 apresenta uma arquitetura específica; encoders, decoders e variantes atuais não devem ser descritos como idênticos ao desenho original.[F1]
Q, K e VSão projeções aprendidas; a analogia “procura / combina / transporta” ajuda, mas não substitui o cálculo da atenção.[F1]
TokenizaçãoAs divisões variam conforme o tokenizador; contar palavras não equivale a contar tokens.[F2]
Temperatura e top-pSão controles dependentes do algoritmo e da configuração de geração; temperatura não é uma medida de veracidade nem garante efeito na decodificação gulosa.[F3]
RAG e alucinaçõesRecuperar informação pode fundamentar respostas; é necessário testar recuperação, fidelidade, citações e abstenção. Não existe garantia automática de veracidade.[F4], [F5]
PerplexidadeNão é medida geral de utilidade ou segurança. Comparações exigem mesma configuração de avaliação, dados e tratamento adequado da tokenização.[F3], [F4]
JSON estruturadoUm JSON pode ser sintaticamente válido, obedecer a um esquema e ainda conter informações falsas. Valide tipos, regras de negócio e evidências da fonte.[F6]
Texto → SQLSQL gerado não deve ser executado sem verificar permissões, consultas permitidas e limites; uma transação somente leitura é uma defesa, não uma solução isolada.[F7], [F8]
Segurança de agentesConteúdo recuperado, páginas e arquivos são dados potencialmente hostis; instruções neles embutidas não devem ampliar privilégios da aplicação.[F8]
Pesos abertosDisponibilizar pesos não garante transparência dos dados de treino ou direitos irrestritos de uso. Leia as licenças específicas.[F9]
Uma distinção essencial: um exemplo de SDK apresentado como pseudocódigo não comprova que uma API, importação, nome de modelo ou parâmetro realmente exista. Na publicação de código, separar sempre: exemplo conceitual, executável testado e execução em produção validada.

3. Exercícios com critérios de aceitação

Esta seção é a contribuição nova. Todos os exemplos devem usar dados fictícios. Nenhum resultado de execução é declarado como aprovado antes de ser efetivamente medido.

01 — Token ou parâmetro?

Explique a distinção em até cinco frases. Depois teste uma mesma frase com dois tokenizadores reais e anote quantos IDs de tokens cada um retornou.

Aceitação: não confundir unidade de entrada/saída com peso treinável; incluir versão e identificador de cada tokenizador; não inventar contagens. [F2]

02 — Reconstruir o fluxo de geração

Desenhe: texto → tokenizador → IDs → embeddings e informação posicional → blocos de modelo → escores → decodificação → texto. Marque o ponto em que a geração se repete.

Aceitação: diferenciar treinamento de inferência; dizer que o fluxo esquematiza um modelo gerador autorregressivo, não todos os modelos.

03 — As quatro formas de adaptação

Apresente o mesmo caso de perguntas sobre um regulamento: pré-treinamento, ajuste fino, prompting e RAG.

Aceitação: explicitar quais processos alteram parâmetros e quais fornecem contexto em tempo de execução. Distinguir documento atualizado de aprendizado armazenado nos pesos.

04 — Extrair uma fatura sem adivinhar

Crie uma fatura fictícia e extraia número, data, moeda e total em centavos da moeda. Se algum campo não estiver no documento, use null, sem inventar valores.

{
  "numero": "TESTE-001",
  "data": "2026-11-22",
  "moeda": "BRL",
  "total_centavos": 12500
}

Aceitação: (1) JSON válido; (2) esquema e tipos corretos; (3) data de calendário válida; (4) moeda explicitamente identificada; (5) correspondência dos valores com a fatura; (6) revisão de divergências por pessoa autorizada. Os dados acima são apenas um exemplo fictício, não uma extração executada. [F6]

05 — Recuperação e resposta não são a mesma nota

Formule dez perguntas com respostas verificáveis sobre documentos públicos, incluindo duas sem resposta no acervo. Separe recuperação hit@k, suporte factual, correção das referências e abstenções.

Aceitação: registrar documentos, versão, trechos relevantes, resposta e resultado por questão. Não usar uma única taxa de acerto para afirmar que todo o sistema é confiável. [F5]

06 — Classificar reclamações de teste

Elabore 20 reclamações fictícias com rótulos revisados por humano, incluindo casos ambíguos e casos com múltiplos assuntos. Compare a classificação do sistema com esse gabarito.

Aceitação: taxonomia explícita, matriz de confusão ou contagem por classe, erros comentados e conclusão limitada ao pequeno conjunto de teste. Não extrapolar desempenho para o mundo real.

07 — Avaliar respostas com uma rubrica

Dê notas de 0 a 2, separadamente, para correção, relevância, completude, fundamentação e conformidade ao formato. Compare duas respostas à mesma pergunta.

Aceitação: justificar cada nota com evidência; informar avaliador, amostra, prompt e versão. Não misturar uma impressão de fluência com prova factual. [F4]

08 — Texto para SQL com proteção

Desenhe uma aplicação que transforma pedidos em consultas a um banco fictício: expor somente o esquema autorizado; bloquear escrita; impor permissões no servidor; validar sintaxe, tabelas e limites; parametrizar valores; inspecionar o plano; registrar a revisão.

Aceitação: comandos que alteram dados são rejeitados mesmo quando disfarçados de pedido legítimo. Testes negativos devem provar o bloqueio; não executar SQL produzido pelo modelo diretamente contra banco real. [F7], [F8]
