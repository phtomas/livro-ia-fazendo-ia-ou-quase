10 conceitos essenciais de MCP

Como uma aplicação com IA conversa com ferramentas, bancos de dados e programas externos? O Model Context Protocol (MCP) padroniza essa integração. Aqui estão seus dez conceitos centrais, em português, com correções, um mapa visual editável e exemplos de bancada.

Da aplicação ao servidor: os dez conceitos

01 / APLICAÇÃO

Host

É o programa com o qual a pessoa interage, como uma IDE, assistente ou aplicação própria. Coordena a experiência, os clientes MCP, os controles de segurança e a disponibilização de ferramentas ao modelo.

Não confunda: o host não é o servidor MCP.

02 / COMPONENTE

Cliente MCP

Componente criado ou gerenciado pelo host para conversar com um servidor específico. Uma aplicação pode operar vários clientes, um para cada conexão lógica com servidores diferentes.

Não confunda: cliente MCP e pessoa usuária são coisas distintas.

03 / PROVEDOR

Servidor MCP

Programa local ou remoto que disponibiliza capacidades ao cliente: tools, resources e prompts. Um servidor pode expor somente parte dessas capacidades.

Exemplo: servidor que oferece funções de um aplicativo de CAD.

04 / AÇÃO

Tools — ferramentas

São operações invocáveis, com nome, descrição e esquema de argumentos. Um modelo pode pedir a chamada de uma ferramenta; a aplicação autoriza, executa a operação no ambiente apropriado e devolve o resultado.

Exemplo: listar_componentes ou gerar_relatorio.

05 / CONTEXTO

Resources — recursos

Dados expostos ao cliente e identificados por URI, como documentos, arquivos, relatórios ou esquemas. O aplicativo decide quando e como apresentar esse conteúdo ao modelo.

Importante: expor um recurso não significa carregá-lo automaticamente.

06 / MODELO DE INSTRUÇÃO

Prompts

Modelos de interação fornecidos pelo servidor, muitas vezes com parâmetros, para tarefas recorrentes. A interface pode apresentá-los em menus ou atalhos.

Correção: comandos iniciados por / são uma convenção de algumas aplicações, não exigência do MCP.

07 / COMUNICAÇÃO

Transporte

Define como as mensagens chegam ao servidor. Os transportes padronizados incluem stdio, útil para processos locais, e Streamable HTTP, útil em serviços acessados por rede.

Correção: um servidor local pode ser acessado remotamente conforme a infraestrutura; “local” e “remoto” não são propriedades do protocolo em si.

08 / MENSAGENS

JSON-RPC 2.0

É a estrutura das requisições, respostas e notificações MCP. Métodos como tools/list e tools/call organizam as operações.

Não confunda: JSON-RPC é a linguagem das mensagens; stdio e HTTP transportam essas mensagens.

09 / SEGURANÇA

Autenticação e autorização

Identidade e permissões são necessárias quando um servidor protege recursos ou operações. Em HTTP, a especificação contempla fluxos baseados em OAuth; em stdio, credenciais podem vir do ambiente do processo.

Não é automático: a existência de MCP não garante que uma ação seja segura ou autorizada.

10 / DESCOBERTA

Registry — catálogo

Catálogos ajudam a localizar servidores publicados, descrições e metadados. A verificação do fornecedor, do código, das permissões e da origem do pacote continua sendo responsabilidade de quem instala.

Correção: aparecer no catálogo oficial não é garantia de qualidade ou ausência de riscos.

Uma experiência de bancada, sem expor dados privados

Imagine um aplicativo com IA conectado a um servidor MCP que disponibiliza ferramentas de um programa de projeto eletrônico. A pergunta humana é: “Liste os componentes deste esquema e destaque os resistores sem valor.”

Pessoa→Host com IA→Cliente MCP→Servidor CAD→Resultado→Verificação

O servidor disponibiliza sua ferramenta; o cliente encaminha a chamada; o programa faz a leitura permitida do esquema e retorna dados. O modelo interpreta o retorno, mas não substitui a verificação dos resultados. Um procedimento de geração ou alteração de arquivos deve usar permissões estritamente necessárias e, quando pertinente, exigir confirmação explícita.

Experimento do leitor: (1) identifique host, cliente e servidor; (2) liste as ferramentas publicadas; (3) execute somente uma consulta de leitura; (4) compare o retorno com a fonte real; (5) registre a versão MCP e os logs sem incluir tokens, chaves ou endereços privados. Resultado esperado: uma evidência reproduzível do que de fato foi executado.

Atualização da especificação: o que mudou em 2026?

A revisão 2026-07-28 trouxe mudanças relevantes no ciclo de vida do protocolo. Tutoriais da linha 2025 continuam úteis para ambientes que usam versões anteriores, mas não devem ser tratados como descrição universal das implementações atuais. Comunicado oficial de lançamento.

TemaRevisões anteriores (até 2025-11-25)Revisão 2026-07-28
InicializaçãoTroca initialize/initializedNúcleo sem sessões; cada pedido inclui metadados apropriados de versão e capacidades
DescobertaNegociação no início da conexãoserver/discover opcional
HTTPStreamable HTTP com mecanismos anteriores de sessãoCabeçalhos como Mcp-Method e Mcp-Name; regras atualizadas de transporte
EventosAlguns mecanismos de assinatura e requisições iniciadas pelo servidorModelo de assinaturas e solicitações de entrada revisado, com subscriptions/listen e MRTR
CompatibilidadeSDKs e hosts podem usar fluxos clássicosÉ necessário conferir a versão efetivamente suportada por host, cliente e servidor
Segurança antes da comodidade: um servidor MCP pode expor dados ou executar operações sensíveis. Não instale pacotes desconhecidos apenas porque aparecem em um catálogo. Confira código ou fornecedor, permissões, isolamento, identidade do servidor, escopos e registros de auditoria. Não copie segredos para prompts ou repositórios públicos.

O que este complemento acrescenta ao livro?
